# 踩坑清单

按"**现象 → 真因 → 不能怎么改**"整理。每条都是实际发生过的，
且**大部分第一次的判断都是错的**（我标了"我误判过"的地方）。

接手前建议通读一遍：这些坑的共同特点是**症状和真因看起来完全不像**，
不知道就会往错的方向改。

---

## 1. 录音会把画面一起录进去（最严重，我误判过）

**现象**：采集"一切正常"、上传"成功"，但识别服务**每块都返回空文本**，一条字幕都没有。

**真因**：`video.captureStream()` **不带参数**时返回的流**同时含视频轨和音频轨**。
整个交给 `MediaRecorder` 会把画面也录下来：

| | 正常 | 出错 |
| --- | --- | --- |
| 12 秒的块 | 约 96KB | 1.4 ~ 3.4 MB（约 2.3Mbps） |
| 送到识别服务 | 正常识别 | **解不出音轨，返回空文本** |

**我误判过**：一度以为是跨域、格式不支持、播放器特殊实现，查了好几轮。
**真正指出问题的是"每块多少 KB"这一行日志** —— 加上它才定位到。

**约束**：`src/content/audio-source.js` 的 `audioOnlyStream()` 必须保留，
它负责剥掉视频轨。有专门的回归测试守着（`audio-source.test.mjs`）。

**判断标准**：只录音频时，**12 秒的块应在 100KB 上下**；超过 300KB 就不正常。

## 2. 跨进程传二进制会丢类型（连续踩三次，我误判过两次）

**现象**：内容脚本报"本地 98KB"，后台收到 0 字节或"未知二进制形态(object)"，
每块都识别失败，而日志里数据大小一切正常。

**真因**：这台机器上 `chrome.runtime.sendMessage` **不保留二进制对象的类型**：

| 传输方式 | 后台实际收到 |
| --- | --- |
| Blob 对象 | 0 字节 |
| ArrayBuffer | 未知二进制形态(object) |
| TypedArray | 同样降级成普通对象 |
| **base64 字符串** | ✅ 稳定可靠 |

**约束**：音频一律用 base64 字符串传输（`common/binary.js`）。
`binary.test.mjs` 里有一条测试专门锁住"必须用 base64、不得传二进制对象"。

---

## 3. 类型判断不能用 `instanceof`（跨 realm 会失效）

**现象**：明明是合法的 ArrayBuffer，却被判为"不是有效的字节数据"。

**真因**：`instanceof` 依赖 JS 执行环境（realm）。`blob.arrayBuffer()` 返回的对象
可能来自另一个 realm，`x instanceof ArrayBuffer` 会返回 false。

**约束**：`common/binary.js` 用**特性检测**（看 `byteLength`/`byteOffset` 这些结构特征），
不用 `instanceof`。这个坑是测试逼出来的 —— 真实浏览器里极难复现。

**同类坑**：`DataView` 没有 `length` 属性（只有 `byteLength`），
用 `typeof x.length === 'number'` 判断会漏掉它。

---

## 4. `isTypeSupported()` 说支持，`start()` 却抛 NotSupportedError

**现象**：`MediaRecorder.isTypeSupported('audio/webm;codecs=opus')` 返回 true，
但带 `{mimeType, audioBitsPerSecond}` 调用 `start()` 抛 `NotSupportedError`。

**真因**：`isTypeSupported()` 只回答"理论上支持这个容器"，
**不保证这台机器上真的能录**。

**约束**：`capture.js` 的 `buildRecorderOptions()` 给出一串备选参数，
逐个实测，最后必然试一次"不带任何约束"（把选择权交给浏览器）。
失败组合会被记住并跳过，不会反复重试。

---

## 5. 视频暂停时录音会得到 0 字节

**现象**：报"音频数据无效或为空"，或显式格式时报 `NotSupportedError`。

**真因**：暂停的视频不产生音频数据，此时启动 MediaRecorder 两种结果都没有意义。

**约束**：
- `AudioChunkCapturer.start()` 在媒体暂停时**不开窗口**，等 `play` 事件
- `handlePlaybackChange()` 在暂停时**丢掉正在录的窗口**（否则时间戳会横跨暂停区间）
- **空音频块绝不上传**（`handleChunk` 里有两道空块判断）

**注意**：单个空块是正常的（用户常在"开启字幕后才点播放"），
**连续 3 块空**才说明流本身有问题、才值得切换采集方式。

---

## 6. 本地 Whisper 需要 WAV，而 MediaRecorder 给的是 WebM

**现象**：本地服务报解码错误，或需要装 ffmpeg。

**真因**：云端服务有完整解码能力，能直接吃 WebM；本地服务通常没有 ffmpeg。

**约束**：扩展侧用 `content/wav-encoder.js` 把录音转成 **16kHz 单声道 WAV**
（Whisper 就是按 16kHz 训练的，对齐它省掉服务端重采样）。
这样本地服务只需要 Python 标准库的 `wave` 模块。
`wav-encoder.test.mjs` 逐字段核对 WAV 头，改错一个字段都会失败。

## 7. 字幕用百分比定位会跑到视频外面（我误判过）

**现象**：识别成功、面板上"已生成 N 条字幕"在涨，但**画面上什么都看不到**。

**真因**：字幕层挂在 Shadow DOM 内的固定定位容器里，`bottom: 8%` 依赖
"包含块"的解析；解析异常时字幕就落到视频外面了。

**约束**：`overlay.js` 的 `applyCaptionPosition()` 用**像素**定位，
按视频实际高度计算，并保证留白不小于字号、不超过视频高度的三分之一。

---

## 8. 悬浮面板会压住字幕（位置改了三次）

**历史**：右下角（默认，用户习惯）→ 压住视频底部字幕 → 改左上角 →
盖住课程正文顶部 → **最终做成可配置，默认回到右下角**。

**约束**：位置由设置项 `panelPosition` 控制，四个角可选。
`positionPanel()` 切换时**必须清空其它方向的偏移** ——
否则从右下角切到右上角时 `top` 和 `bottom` 同时存在，面板会被拉成一条长条。

**诊断**：`overlay.inspect()` 会报告"④ 未被控制面板遮挡"，
以及"〇 字幕层未被隐藏"（后者曾漏掉，导致一轮排查走偏）。

---

## 9. 字幕会"闪一下就没了"（连贯性）

**现象**：字幕偶尔出现一下，中间大片空白，很不连贯。

**真因**：两个叠加
1. 文字按字数比例摊到整块时长上，短句只分到零点几秒
2. 渲染循环一遇到"当前时刻没有对应字幕"就清空 ——
   而块与块之间必然有间隔（等下一块 + 识别耗时）

**约束**：
- `SubtitleTrack` 给每条字幕补足**最短显示时长**（默认 1.2 秒）
- `renderFrame()` 一旦显示某条就**保留到被下一条替换**（上限 `holdSeconds`）
- 只有两种情况才清空：**拖动进度条**（内容已对不上）和**视频暂停**

**注意**：`renderFrame()` 是从 `renderLoop()` 抽出来的，为的是能直接测 ——
"该保留还是该清空"是最容易出错、最需要测试的判断。

---

## 10. 自动降级不能改写用户设置（我犯过这个错）

**现象**：明明元素模式可用（诊断录到 156KB、峰值 1.0），插件却一路报错
`Cannot capture a tab with an active stream`。

**真因**：我把"自动降级到标签页模式"的结果**写进了保存的设置**，
于是 `captureMode` 被永久改成 `tab`，此后每次开启字幕都强制走那条坏路。

**约束**：降级只写 `sessionCaptureMode`（会话级），**绝不调用保存设置**。
`auto-attach.test.mjs` 有一条测试专门断言"降级不得发出任何 save-settings 消息"。

**同类坑**：`start()` 开头不能无脑清空 `sessionCaptureMode` ——
否则降级刚设上就被自己清掉。现在用 `keepSessionMode` 选项区分。

---

## 11. Chrome 同一标签页只允许一个抓取

**现象**：`Cannot capture a tab with an active stream`。

**真因**：我为了"抓取后把声音接回扬声器"申请了**两个** streamId（一个录音、一个回放），
Chrome 直接拒绝。

**约束**：
- `background` 里**只申请一个** streamId
- 重新申请前必须**先释放上一次**（`releaseTabStream`）
- 遇到该错误时**等待 600ms 重试一次**（是时序问题，重试通常就好）
- 离屏文档**不得自己消费 streamId**（`content-scripts.test.mjs` 有断言守着）

---

## 12. `tabCapture` 必须由扩展页面消费 streamId

内容脚本和 service worker 都不行（service worker 里没有 `getUserMedia`）。
这就是 `src/offscreen/` 存在的原因 —— 它只提供扩展侧上下文，不采集音频。

---

## 13. 空音频块被报成"识别失败"会误导用户

**现象**：用户去反复检查 API Key，而其实只是视频还没播放。

**约束**：空块措辞必须是"**没有采集到音频内容（视频可能还没开始播放）**"，
**不能说成"识别失败"**。而且这类错误**不计入连续失败次数**
（否则用户刚点开启字幕、还没按播放，就会被判"连续失败"而中止）。
`asr-client.test.mjs` 有测试锁住措辞。

---

## 14. 刷新扩展后必须刷新页面（最高频踩坑点）

**现象**：点"开启字幕"说"**还没配置识别服务**"；改了设置"好像没生效"；
悬浮球消失。

**真因**：内容脚本**只在页面加载时注入**。刷新扩展后，视频页面里跑的还是旧脚本，
它和扩展的联系已经断了。

**约束**：
- `ensureSettings()` **只在成功读到配置时才缓存**（失败不能缓存成空对象）
- 要区分"**读取失败**"和"**真的没配**" —— 前者提示刷新页面，后者引导去设置
- `isExtensionAlive()` 用 `chrome.runtime.id` 判断连接是否还在
- 悬浮球被删掉后要能**自愈**（`attachOverlay()` 检查节点是否还在文档里）

**正确流程**：改设置/刷新扩展 → **刷新视频页面（F5）** → 播放视频 → 开启字幕

## 15. `faster-whisper` 与 `av` 版本不兼容

**现象**：`TypeError: open() got an unexpected keyword argument 'metadata_errors'`，
**任何输入**都失败。

**真因**：`faster-whisper 1.2.1` 调用 `av.open(..., metadata_errors=...)`，
而 `av 19.x` 删掉了这个参数。且 `transcribe()` 开头**无条件**调用解码，所以必然踩中。
降级 `av` 也不行 —— 旧版在 Python 3.13 上没有预编译包。

**约束**：`server.py` 的 `patch_av_open_compat()` 接管 `faster_whisper` 的解码入口：
采样数组直通、WAV 走标准库、其它格式自动忽略多余参数。
**注意要替换 `faster_whisper.audio` 模块里的 `av` 名** ——
它是 `from av import open` 导入的，改 `av` 模块本身无效。

## 16. HuggingFace 在国内连不上

**现象**：模型下载 `ConnectTimeout`。

**约束**：`server.py` 默认把 `HF_ENDPOINT` 指向 `https://hf-mirror.com`，
且**必须在 `import faster_whisper` 之前设置**（库在导入时就读并缓存了）。

**同类**：清华 PyPI 镜像会返回 403，装依赖用官方 PyPI 或阿里云镜像。

## 17. Whisper 在静音/非语音上会编内容

**现象**：纯音调音频被识别成"字幕by索兰娅"这种莫名其妙的话。
**假字幕比没有字幕更糟**，因为用户无法分辨。

**约束**：`server.py` 的 `audio_is_silent()` 先看能量（RMS），
静音直接返回空文本，不送模型。扩展侧也有一道静音判断。

---

## 18. 云端识别的延迟优化不动（架构限制）

**现象**：字幕明显落后于语音 10~20 秒。

**真因**：日志显示"落后 ≈ 识别耗时"，即**全部时间花在等服务端返回**。
硅基流动的 `/audio/transcriptions` **只有批量接口、没有流式**，
所以延迟 ≈ 分块时长 + 服务识别耗时 ≈ 6 + 9 ≈ **15 秒**。

**这是架构层面的天花板，插件里怎么调都突破不了。** 已通过改用本地 Whisper 解决
（识别耗时降到 1.4~2.5 秒）。

**别再做的事**：不要试图靠调分块大小或换云端模型把它压到实时 —— 做不到。
换模型能买到的是**准确率**（见 #35），不是更低的延迟。

**第六轮补充（2026-10）**：上面「硅基流动只支持两个转录模型」的说法**已过时**。
现在它的模型广场里 `Qwen/Qwen3-ASR-1.7B`、`XingChenAGI/XingChenASR-V3.2-Ultra`
都能从 `/audio/transcriptions` 调用，且标价免费。识别准确度因此可以显著改善，
但**延迟不变**——延迟由「分块秒数 + 服务端排队」决定，与模型多准无关。

## 19. 别用 `--dump-dom` 或带 `--load-extension` 的 headless Edge（本机）

- `--load-extension` 在 headless 下会让浏览器直接启动失败
  （报 `Multiple targets are not supported in headless mode`），
  所以**无法在终端里验证扩展加载**
- `--dump-dom` 同样不可用
- 我写过 CDP（调试协议）方案，也卡住了，已删除

**结论**：本机没有可用的"真实浏览器里跑扩展"的自动化手段。
验证要么靠单元测试（142 项），要么**请用户在真实浏览器里测**。

**另外**：清理测试进程时**只按自己的数据目录精确清理**。
我曾用 `Where-Object { $_.MainWindowHandle -eq 0 }` 误杀了用户正在用的 Edge 进程 ——
无窗口不等于 headless，用户的浏览器也有无窗口进程。

## 20. 测试里容易踩的坑

| 坑 | 表现 | 处理 |
| --- | --- | --- |
| 沙箱缺 `chrome.runtime.id` | 测试走“扩展失联”分支却还通过（**假绿**） | 沙箱必须提供 `id`、`onMessage.addListener` |
| 沙箱缺 `setInterval`/`setTimeout` | 新代码一用就报错 | 按需补齐 |
| 主控的巡检是**自续期 setTimeout** | 测试进程永不退出（像卡死） | 调 `__ZIMU__.stopAttachRetry()` 再清定时器 |
| 跨 realm 的 `assert.deepEqual` | 两个 `{}` 却不相等 | 用 `Object.keys(x).length` 这类与 realm 无关的断言 |
| 测试桩件的 `querySelector` 靠 `innerHTML` 注册 | 用 `className` 赋值的节点取不到，测试假失败 | 桩件也要支持 `className` |
| 变异测试**没抓住**注入的错误 | 说明那条断言是空转的 | 检查是不是有重复路径掩盖了它 |
| 断言里直接写字幕文本 | 全角句号会被 `normalizeText` 换成半角，测试假失败 | 用 `normalizeText('原句。')` 比，别硬编码 |

# 第二轮：用户实测反馈（字幕缺内容 / 不连贯）

> 用户现象描述：“出现字幕后该条字幕会持续存在一段时间……等下次字幕更新又会持续一段时间，
> 导致中间的那段字幕直接不显示，还是输出不连贯的问题，视频中的语言没有被字幕完整的表达出来。”
>
> 日志里的关键证据：同一批块的识别耗时是 1.3s / 7.9s / **14.9s** / **73.7s**；
> 块的索引顺序与时间顺序不一致；两次「块覆盖区间」之间有一段谁也没覆盖的空白。

## 21. 块是按**完成顺序**回来的，字幕轨必须自己保证有序

**现象**：一句话说完字幕闪过去，中间那几句**完全没有出现过**。

**真因**：块是异步识别的，`handleChunk` 之间没有任何排队，谁先返回谁先写进字幕轨。
单块识别耗时实测能在同一批里从 1.3 秒抖到 73.7 秒，所以**索引顺序 ≠ 时间顺序**
（实测：第 7/8/9/10 块分别覆盖 552.7 / 583.0 / 578.5 / 589.5 秒）。
而 `segments` 原来是直接 `push` 的，一旦乱序：

- `segmentAt()` 的二分查找会走到错误区间，返回 `null`；
- `lastSegmentBefore()` 遇到第一个“还没结束”的就 `break`，返回一条更早的。

两者叠加，该显示的字幕被**整条跳过**。

**约束**：`SubtitleTrack.addChunk()` 必须**按时间有序插入**（`insertIndex()` + `splice`），
不能 `push`。重叠收尾只能对照“插入位置前面那一条”——
拿数组最后一条去比，会把迟到的旧块整段挪到几十秒之后，内容就废了。

---

## 22. 识别一旦落后，整块字幕会被渲染层整体跳过

**现象**：一条字幕挂很久，下次更新又挂很久，中间的内容看不见。

**真因**：`renderFrame()` 只认两条路——`segmentAt(当前时间)` 命中，或者
`lastSegmentBefore(当前时间)`。识别落后时，一整块的字幕**全部**落在当前播放位置之前，
`segmentAt` 一条也命中不了，于是只剩“该块的最后一句”能显示，还被 `holdSeconds`
（默认 21 秒）按住。块里其余的句子永远没有机会上屏。

**约束**：`handleChunk` 拿到 `result.added` 后交给 `enqueueLaggingSegments()`，
把 `end <= 当前播放位置` 的段放进 `catchUpQueue`，由 `renderFrame` 逐条补显。
三件事别改坏：

1. 队列长度 ≤ 1 时**不节流**，立刻显示。否则倍速下每 2.5 秒来一块、节流 4 秒一条，
   积压只会越滚越大（这个坑是改的时候自己踩到的）；
2. 停留时长取该条的**原始时长**（夹在 0.9~4 秒）；积压 ≥ 8 条时压到 1.2 秒，
   否则补显速度低于产出速度，永远追不上；
3. 拖动进度条 / 停止 / 清空时必须 `resetCatchUp()`，否则会补显与画面无关的内容。

**导出不受影响**：队列满了会丢掉最早几条的**补显**，但它们仍然完整保存在
`track.segments` 里，导出 SRT 一条不少。

---

## 23. 恢复播放时故意等一个分块周期，等于在音频里挖洞

**现象**：字幕成段地缺内容，而且缺口常常紧跟在“暂停过一下”之后。

**真因**：`handlePlaybackChange()` 恢复播放时写的是
`nextWindowAt = now() + chunkSeconds * 1000` ——**故意等满一整个分块周期才开始录**。
每暂停一次，音频里就多一个 `chunkSeconds` 长的洞，**那段时间的声音从来没被采集过**，
识别再准也补不回来。实测日志：第 7 块结束在 565.6s，下一块却从 578.5s 才开始
（12.9 秒空白）。

**约束**：恢复播放后 `nextWindowMediaAt = currentTime()`，必须**立刻**开窗。
起头那一块偏短没关系，`finalizeSession` 会丢掉不足 1.5 秒的块。**宁可少一块，不能缺一段。**

## 24. 窗口按墙钟计时，倍速播放下分块长度就错了

**现象**：日志里“第 N 块：x→y”的跨度明显大于设置里的“每块秒数”，倍速越高越离谱。

**真因**：`scheduleTick()` 原来用 `performance.now()` 判断开窗与关窗，
但配置项 `chunkSeconds` 的语义是**每块多少秒音频**。倍速播放时一段墙钟时间里流过的
音频是成倍的（实测 4 秒窗口装进 12.9 秒音频），识别负载凭空翻倍；
更糟的是页面主线程一卡、`setTimeout` 被推迟，原来的追赶逻辑
`if (nextWindowAt <= t) nextWindowAt = t + chunkSeconds` 会**直接跳过中间若干个窗口**，
又是一处音频空洞。

**约束**：开窗节奏与关窗判据都改用 `video.currentTime`。
另外保留一条**墙钟兜底**（`max(chunkSeconds * 4, 30)` 秒）：视频卡住时 `currentTime`
不推进，只靠媒体时间这个窗口会永远开着、永远不产出字幕。
启动时会把 `playbackRate` 打进日志，倍速问题一眼可查。

---

## 25. 同一块音频被解码三遍（全在页面主线程上）

**现象**：识别耗时在同一批块里剧烈抖动（1.3s / 7.9s / 14.9s / 73.7s），块还成对返回。

**真因**：`handleChunk()` 里连着调了两次**完全相同**的 `measureLoudness(chunk.blob)`
（两次 `decodeAudioData`），发送时 `toWavBuffer()` 又解码第三次。
三次解码 + 重采样 + 逐样本 WAV 编码全部落在页面主线程上，每块都要做一遍。
主线程被占就会推迟分块定时器，进而触发第 24 条里的窗口跳过。

**约束**：解码只做一次——`wav-encoder.js` 的 `decodeChunk()` 同时给出 PCM 和响度，
主控用它做静音判定，编 WAV 时复用同一份 PCM，编完立刻把 `samples` 置空。
`toWavBuffer()` 继续保留（返回值里也带上 `rms`/`peak`），因为它有独立测试。

**顺带一提**：后台对 `zimu:transcribe` 是**无排队**的，识别服务端又用
`MODEL_LOCK` 串行处理。所以只要出现“服务比产出慢”，等待时间就会线性堆积——
上面那串 73.7 秒的耗时就是积压的表现，不是模型突然变慢。

## 26. 绝不关掉**最后一个**录音窗口（会漏内容，最难自查）

**现象**：用户说“字幕输不全”。回看日志发现第 0 块结束于 **896.9s**，
第 2 块却从 **908.2s** 才开始——中间 11.3 秒**连一条“第 N 块”的日志都没有**。

**真因**：窗口开合完全依赖巡检（`scheduleTick`）。页面主线程一忙，巡检被推迟，
**正在录的窗口却已经被关掉**，而新窗口要等下一次巡检才开。那段“没人录音”的
时间里，音频**没有留下任何副本**——识别服务再准也补不回来。
这不是识别质量问题，是采集问题，而且日志里最安静（连块都不产出），最难定位。

**约束（覆盖不变式）**：视频在播时，任何一刻都必须有窗口在录。
`closeSessionIfCovered()` 是唯一的关窗入口，`sessions.length <= 1` 时**拒绝关闭**。
宁可让这个块录长一点（识别慢些、延迟高些），也不能出现空档。

**推论**：延迟和完整性在这里是**冲突**的。默认站完整性——用户能忍慢，
不能忍缺内容。所以墙钟兜底（`max(chunkSeconds*2.5, 10)` 秒）也会被这条挡住。

**怎么验证它没退化**：`__ZIMU__.inspect()` 里的「采集空档：N 处」常年应为 0；
控制台出现 `⚠ 采集空档 a→b` 就说明这段音频真的没录到，不是识别不准。

## 27. 「分块节拍被推迟」是上面几类故障的共同上游

**现象**：块被录长（6s 的窗口录成 12s）、识别耗时随之翻倍、还可能留下空档。

**真因**：巡检是 `setTimeout`。页面主线程被长任务占住，或浏览器对定时器限流，
巡检就会迟到好几秒。窗口该关的没关（录长）、该开的没开（空档）。

**处理（三条独立的触发路径，任一条有效即可）**：

1. 巡检间隔收到 **200ms**；
2. 再挂一条 `video.timeupdate` 驱动 —— 它由媒体管线触发，和 `setTimeout` 不是同一条路；
3. 每个窗口另排一个**到点必关**的定时器（`armSessionDeadline`），按播放倍速把
   “媒体秒”换算成墙钟毫秒。

**必须能看见**：巡检间隔超过 1.2s 就打 `⚠ 分块节拍被推迟 X.Xs`；
块长超过 `chunkSeconds × 1.25` 就打 `⚠ 第 N 块超长`。没有这两行日志，
就只能对着一个 12 秒的块猜原因。

**注意**：`timeupdate` 和 `setTimeout` 都在主线程上，主线程被**彻底占死**时两条都停。
那种情况下只能靠覆盖不变式兜底（块变长，但不丢内容）。

## 28. 别用单一指标判断“识别快不快”——先分清是哪一段慢

**现象**：用户说“字幕太慢”，但日志里的耗时数字看着还行。

**关键**：端到端延迟 = **等分块** + **识别耗时**，两段的优化手段完全不同。
第一次定位时就差点走错方向——块长 12.0s、窗口间隔 11.1s（正好是
`chunkSeconds - overlap`），说明慢在**分块设置**而不是识别。

**约束**：`start()` 时必须把生效参数打出来：
「分块设置：每块 Xs 音频，重叠 Ys」。
看到这块块的「音频 X.Xs」和这个值对不上，问题就在采集侧，不用去查服务。

**想单独测识别速度**（不受页面影响）：停掉扩展，直接跑

```powershell
python tools\local-asr\verify-speech.py
```

它自己合成中文语音再送去识别，给出 `速度 ?.?x 实时`。
如果这里是 3 倍实时、而扩展日志里却是 1 倍实时，说明页面在抢 CPU，
不是识别服务的问题。

## 29. 「回看时字幕准确」这句话本身就是最好的诊断

**现象**：实时播放时字幕滞后、滞留、前后不连贯；但**往回拖**去看刚播过的部分，
字幕一条不差、时间点也对。

**推论（能省掉很多排查方向）**：说明**识别结果本身是完整的**，字幕轨里存着正确的
文本与时间。问题 100% 出在「实时追赶」这一段——识别跑得比播放慢，当前时刻没有
可用字幕，渲染层只能退到“最近一条”或落后的补显队列。
所以不必再去查识别质量、音频采集、时间戳对齐，那些都是对的。

**反过来也成立**：如果连回看都不准（错字、缺句、时间点漂移），那才是识别或采集的
问题，去查第 26 条与服务端日志。

## 30. 屏幕字幕必须有**落后上限**，否则补显会变成“回忆录”

**现象**：用户说“一句话长时间滞留在屏幕上，过一会儿换一句，而新句和上一句不连贯，
视频里好像已经说过很多话了”。

**根因**：为了不让迟到的内容被整块跳过，项目里有「追赶队列」（见第 22 条）。
但补显节奏原本按字幕**自然时长**走，等于用同样的速度追同样的距离——只要识别
慢过一次，这段落后就被**永久保留**；队列越积越多时，屏幕上是几十秒前说的话，
与画面彻底脱节。分块设为 12 秒时尤其强烈。

**修法（三条一起才有效）**：

1. **当前时刻的字幕优先**：`segmentAt(time)` 命中就直接显示并清空队列。否则当前
   内容会被历史补显挡住——用户的原话是“Console 里明明有文字返回，屏幕上却不动”。
2. **落后上限** `maxLagSeconds = max(6, chunkSeconds)`：队列里最新一条的 `end`
   距当前播放时间超过它，就丢掉队列、直接对齐最新。**屏幕求跟得上，文件求不丢**——
   被跳过的内容仍完整留在字幕轨里，导出 SRT 一条不少。
3. **补显快于实时**：`catchUpDwellFor()` 取自然时长的**一半**（夹在 700~2200ms）。
   与实时同速是不可能追平的，这一点当初想反了。

**注意**：`maxLagSeconds` 同时决定“多大的落后还值得逐条补显”。调大它字幕更完整
但更滞后，调小则更及时但会跳过更多中间内容。这是**产品取舍**，不是纯技术参数。

## 31. 一个阈值不要背两份职责：`holdSeconds` 的教训

**原来的写法**：`renderFrame()` 里有一条“持有上限”（`chunkSeconds × 2.5 + 6`，
分块 12 秒时高达 **36 秒**），它同时被用来做两件事：

1. 块与块之间**别把字幕清空**（连贯性要求它**大**）；
2. 用户拖了进度后**别显示旧位置的字幕**（正确性要求它**小**）。

**结果**：识别一落后，时间差很容易超过上限 → 屏幕被清空 → 用户以为插件坏了；
而真正需要它生效的“拖进度”场景，又因为值太大而迟滞。

**改法**：拆成两件独立的事。

- “保留最近一条”**不再有时间限制**——只要有内容就显示，落后多少交给诊断行如实报出。
- “跳转点之前的内容不显示”改用**独立的 `lastJumpMediaTime`**：`onTimelineJump()`
  记下跳转位置，渲染时凡 `end < jump - 1` 的字幕一律不显示。

**教训**：一个阈值服务两个方向相反的需求，最后一定两边都不对。看到某个常量被两种
理由引用，就该拆。

## 32. 流式识别下，**幻觉会被「一致前缀」主动定稿**（比批量模式更危险）

**背景**：实时链路用「相邻两次解码的最长公共前缀」决定哪些字可以定稿
（LocalAgreement）。这个机制的前提是「模型在相同音频上给出相同文本 = 稳定」。

**坑**：非语音（音乐、音效、纯音）上 Whisper 会**编内容**，而它在同一段音频上
编出来的东西是**高度可复现**的——于是两次解码一致 → 前缀判定为「稳定」→ **定稿**。

实测（`small` / `int8` / `zh`）：

| 输入 | no_speech_prob | avg_logprob | 结果 |
| --- | --- | --- | --- |
| 真实中文语音 | 0.002 | −0.191 | 正常 |
| 220Hz 正弦音 | **0.845** | **−0.840** | 编出「字幕製作人Zither Harp」 |
| 纯静音 | — | — | 无输出 |

批量模式下这种内容最多出现在一块里；流式模式下它会**进入正式字幕轨**，
而且因为「一致」还会反复出现。课程视频的音乐片头/过场是高频触发场景。

**改法**：`server.py` 的 `is_hallucination()`——`no_speech_prob > 0.6` **且**
`avg_logprob < -0.5` 才丢弃，两条同时成立才判为幻觉。

**两个反直觉的点**：

1. **Whisper 自带的 logprob 门限（−1.0）挡不住它**：正弦音是 −0.840 > −1.0。
   必须比自带门限更宽松（更接近 0）才有效——别照抄上游默认值。
2. 已有的 `audio_is_silent()` 能量门限**也挡不住**：正弦音能量不低。
   两者是互补关系——能量门挡静音，置信度门挡「有能量但不是人声」。

**教训**：给「稳定」下定义时要想清楚**错误的内容也可以很稳定**。

## 33. 流式的延迟下限是**模型属性**，不是架构能优化的（先量再承诺）

**背景**：上一条整改计划里我写过「流式可把延迟从约 6 秒降到 1~2 秒」。
实测把这个说法证伪了，记录数据避免以后再犯。

**实测**（真实中文语音，从缓冲为空开始逐 1 秒投喂）：

| 缓冲长度 | 模型输出 | 判定 |
| --- | --- | --- |
| 1.0s | 今天我们 | 太短 |
| 2.0s | 今天我們來學習**現象** | **错** |
| 3.0s | 今天我們來學習線性回歸。 | 截断 |
| 4.0s | …線性回歸,首先看一看。 | 还在变 |
| **5.0s** | 今天我们来学习线性回归,首先看一下这个数据… | **首次定稿** |

投喂步长改成 2 秒，首次定稿推到 **6 秒**。也就是说：

- **首次出字幕的地板约为 5 秒**，换投喂节奏只能微调，压不下去；
- 根因是 Whisper 对短音频**输出本就不稳**（2 秒时会给出错误词），
  必须攒够上下文才稳定；「两次一致」的门槛只是把这个过程放大了约一倍。

**结论（写给以后的自己）**：

- 流式真正解决的是**连续性**（每隔几秒就有新内容，而不是等整块）和
  **时间戳准确性**（服务端给真实起止时间，不再按字数摊），
  以及可以顺手丢掉「追赶队列」那一整套补丁；
- 它**不解决**「首次字幕落后几秒」。要归零延迟只有一条路：
  **提前拿到整片音频、预先转写**（HLS 分片可枚举，见 roadmap P0.5）。
- 想把它当卖点写进文档前，**必须先量**——就是上面这张表。

**教训**：延迟类承诺不要凭原理推，要在真实输入上量出「第几秒才首次定稿」。

## 34. 流式降级时**只改标志位、不改采集窗口**（错字漏字的真因，用户实测发现）

**现象**：Console 里明明写着
`流式识别不可用（…已退回分块模式）`，可紧接着的每一块却是
`第 0 块：273.0s→274.6s，13KB，音频 1.6s` —— **全是 1.6 秒**。

**真因**：`start()` 里采集窗口的长度是**一次性定死的**：

```js
const captureChunkSeconds = this.streamActive
  ? this.settings.streamSliceSeconds || 1.6   // ← 流式：1.6s
  : this.settings.chunkSeconds;               // ← 分段：6s
```

而「这台服务到底支不支持流式」是**发出第一片之后**才由后台告知的。
降级分支只做了 `this.streamActive = false`，**采集器手上的 `chunkSeconds`
还是 1.6**，于是整个会话继续每 1.6 秒切一块送识别。

**为什么后果特别严重**：

| | 6s 一块 | 1.6s 一块 |
| --- | --- | --- |
| 一句话被切断的次数 | 少 | 每 1.6 秒切一次 |
| 每次识别能看到的上下文 | 完整句子 | 半个短语 |
| 单位时长请求数 | 1 | 约 3.75 倍 |
| 云端排队 | 正常 | 明显变长（日志里出现「识别耗时 8.6s」） |

模型拿不到上下文，就会输出「是他过他你」「是越小越小大就是」这种串，
**而且请求数暴增把云端的排队时间也拖长了**，两个症状互相加重。

**修复（两层防线，缺一不可）**：

1. `shouldUseStreaming()`：**开始录音之前**就判断用户开关 + 服务是否在本机。
   云端直接按分块模式起步，根本不开 1.6s 的窗口。
   （判断规则复用 `settings.js` 的 `isLocalRelayUrl`，靠 build.mjs 内联进内容脚本，
   不另写一份。）
2. `fallBackToChunkMode(reason)`：真降级时**必须**调
   `capturer.setChunking({chunkSeconds, overlapSeconds})` 把窗口改回去。
   只置标志位不改窗口，就是本条的 bug。

**回归测试**：`test/streaming-fallback.test.mjs`（含 `setChunking` 的幂等与坏值）。

**判断标准**：日志里出现「已退回分块模式」之后，**下一块的时长必须回到
chunkSeconds**。仍是 1.6s 就说明又漏了第 2 层防线。

## 35. 换模型买到的是**准确率**，不是延迟；别把两件事混着谈

**背景**：用户反馈「错字漏字比较多」，同时问「硅基流动那一排模型哪个更好」。

**实测数据（中文 CER，越低越好，来源见文末）**：

| 模型 | 规模 | AISHELL-1 | WenetSpeech 会议 | 备注 |
| --- | --- | --- | --- | --- |
| **Qwen3-ASR-1.7B** | 1.7B | **1.58%** | **5.88%** | 开源 SOTA，接近商业 API |
| XingChenASR-V3.2 | ? | 字准 97.25%（AIShell2） | 字准 94.26% | 工业级，会做语义规整 |
| SenseVoice-Small（**原默认**） | 234M | ~3.0% | ~7.4% | 非自回归，**不吃上下文** |
| Whisper-large-v3 | 1.55B | 5.14% | 18.87% | 中文场景明显吃亏 |

也就是说 SenseVoiceSmall → Qwen3-ASR-1.7B 大约能把错字**减半**。

**但必须说清楚它解决什么、不解决什么**：

- 解决：错字率、专业术语、「数据机/数据机」这类音近错字；
- **不解决**：字幕比语音慢几秒。延迟 ≈ 分块秒数 + 服务端排队，与模型多准无关。

**一个容易踩的取舍**：XingChenASR 的卖点是「高可读语义转写」——
它会自动精简口语冗余、理顺表达逻辑（可读性评分 4.29）。
**这对字幕恰恰是缺点**：字幕应当尽量忠实原话，被“规整”掉的口语
在用户看来就是**漏字**。所以逐字字幕优先 Qwen3-ASR，
XingChen 只在方言/重口音场景才值得换。

**同一个结论的另一面**：`XingChenGSR`（生成式 ASR）会连带改写文本，
**不适合做字幕**，选模型时避开。

**数据来源**：FireRedASR2S 仓库统一对比表、SURE-EVAL（arXiv 2609.39030）、
Qwen3-ASR 技术报告。口径不完全一致的行已标注。

## 36. 逐字显示的节奏必须来自**这句话自己的音频时长**（绕了两版才对）

这一条有两个版本，第一版是错的却"看起来很像对"。留着它，是因为这个弯很容易绕回去。

### 需求（用户提了两轮，方向相反）

- 第一轮：「一个字一个字出来，不要一下出完。」
- 第二轮：「**要跟随音频中的时间**逐个输出，**不是整句说完之后才把上一句输出出来**。」

### 第一版（已被推翻）：按「到达后的耗时」放字

识别本来就比语音**慢一两句**（这是整个项目的常态）。等这条字幕返回时，
它在视频里的那个时间段往往**已经播完了**。于是第一版得出一个看起来很有道理
的结论：既然时间段已经过完，按时间区间算进度第一帧就是 100%，会整句蹦出来，
那就**别用视频时间了**，改成按"到达之后过了多久"给固定时长（0.75~1.8 秒）放完。

```
识别迟到时：  start────────end            ← 时间段（早已走完）
                        ▲ 文本到手
   进度 = (现在 - 到手时刻) / 1.2s        ← 第一版的算法
```

**它确实解决了"整句蹦出"，但制造了另一个更刺眼的观感**：一句话的音频早就说完了，
字幕才回来，然后用一秒多把整句"突突"地补放出来 —— 用户的评价就是
「**像是整句说完之后，字幕才把上一句输出出来**」。逐字成了一个事后回放。

### 第二版（现行）：按这句话自己的时长放字，锚点分两种

```
放字时长 span = clamp(end - start, 0.8s, 8s)      ← 这句话说了多久，就花多久打完
锚点 anchor  = (time <= end) ? start : time       ← 关键就这一行
进度        = (time - anchor) / span
```

| 情况 | 锚点 | 效果 |
| --- | --- | --- |
| `time <= end`：还没播完就拿到文字（**回看已识别片段**、识别跟得上） | `start` | 进度 = 已说时长/总时长，**字真的在它被念出来时出现** |
| `time > end`：迟到 | `time`（到手那一刻） | 整体后移，但**语速对得上话音**，不再是"事后突突放一遍" |

一句话说完（`time ≈ anchor + span`）恰好放完整句——这不是巧合，是设计目标：
**放字速度 = 语速**，所以出字速度与识别产出速度同频，字幕流不会越积越多。

### 连带的三条约束（每条都对应一个真实会踩的坑）

| 细节 | 做法 | 不这样做会怎样 |
| --- | --- | --- |
| 只增不减 | `shown = max(shown, target)` | 同一帧重复计算会让字数回退 |
| 正在打的那句优先 | 下一句已回来也要把当前这句打完（`renderFrame` 里用 reveal 反造等价段） | 后半截被扔掉，违背「组成一句话后再消失」 |
| 整句上屏要标记 `done` | 追赶补显整句上屏时把 reveal 标成「已放完」，但 `doneAtMs = 0` | 下一帧把它当新句重来，**整句缩回头几个字**像抽搐；或补显刚放完就清屏 |

### 还有一条：`show()` 不能覆盖已完成的 reveal

逐字刚好打完那一帧，`typewriterSlice` 已经把 `doneAtMs`（打完的时刻）记上了。
紧接着 `show()` 里那段"整句显示就标记完成"的逻辑若无脑重建 reveal，
`doneAtMs` 会被清零 →「打完停留一会儿再消失」**永远不会触发**。
所以那里必须写成 `if (!this.reveal || this.reveal.full !== text)`。

**回归测试**：`test/subtitle-continuity.test.mjs` 共 9 条逐字用例，
其中「逐字节奏跟着这句话自己的音频时长走」「迟到时仍然逐字放」
「正在打字的句子不会被下一条截断」分别锁住上面三个坑。

### 「组成一句话后再消失」

用户要的收尾节奏是「一句打完就消失、再出下一句」。所以打完后再停留
`captionLingerMs`（1.5 秒）就清空，并记下 `retiredText` 防止下一帧又把它捞回来重打
（否则会无限循环地闪）。稳态下这样做几乎不留空白：出字速度与识别产出速度同频，
下一条差不多正好在这一刻到手；**真出现空白只说明识别卡住了**——那种时候空着，
比一直挂着一句很久以前说的话更诚实。拖动进度条时 `resetCatchUp()` 会清掉
`reveal` 与 `retiredText`，同一句话可以重新打一遍。

## 37. 字幕底色的两个反向约束：**能调到全透明**，但**阴影不能一起去掉**

**需求**：用户嫌黑框丑，要求可调透明度、最低全透明。

**坑在这里**：把 `background` 调成 `transparent` 时，很容易顺手把
`text-shadow` 也一起清掉——看着更「干净」。但字幕是白字，
一旦底色透明、阴影也没了，**浅色课件上就是白字白底，彻底看不见**。

所以两条规则要一起写：

```js
const alpha = clamp(percent, 0, 100) / 100;
caption.style.background = alpha <= 0.001 ? 'transparent' : `rgba(0, 0, 0, ${alpha})`;
// 底色低于 35% 时反而要加强阴影（描边），否则文字失去承托
caption.style.textShadow = alpha <= 0.35
  ? '0 0 3px rgba(0,0,0,0.95), 0 1px 2px rgba(0,0,0,0.95)'
  : '0 1px 2px rgba(0,0,0,0.9)';
```

**测试**：`test/overlay-position.test.mjs` → 「底色浓度可调，拖到 0 时底色完全透明」，
同时断言了 0% 时 `text-shadow` 仍然存在。越界值（999 / -5）也要被夹住。

## 38. 字幕「位置太高」的真身是那条 **12% 硬下限**，不是默认值

用户反馈：「位置太高了，字幕要跟底部悬浮窗平行。」

排查发现 `bottomPercent` 默认 8% **不是**真正的元凶。`applyCaptionPosition()` 里
还有一条：

```js
const preferred = Math.max((videoHeight * this.bottomPercent) / 100, videoHeight * 0.12);
//                                              ↑ 这一条在 600px 高的播放器上 = 72px
```

**它把任何小于 12% 的设置都顶回 12%**：滑块拖到 0 也没用，600px 的视频上字幕
永远钉在离底 72px 处——屏幕上就是「飘在半空」。这条下限是早期为了躲页面
悬浮控件加的，现在有更好的解法（可收起的悬浮窗，见下），该退休了。

**改法**：只保留 `minGap = fontSize + 6`（大字不贴边），上限仍是 `videoHeight/3`，
默认值 8% → 6%。

**遮挡问题的正解**：字幕压在底部居中、面板默认也在右下角，两者注定打架。
与其反复调位置，不如让**面板能收起来**——收起后滑到视频侧边、只留一条窄边
（`translateX(calc(100% - 18px))`），点一下展开。用 `transform` 而不是
`display:none`：收起来之后**必须还能点回来**。

**一个连带的坑**：收起状态下的点击要用**捕获阶段**拦下来。
否则这次点击会先落到悬浮球上，顺手把卡片也点开，变成一个
「既展开又开着卡片」的混乱状态。

```
panel.addEventListener('click', (e) => {
  if (!this.collapsed) return;
  e.preventDefault(); e.stopPropagation();   // ← 必须在捕获阶段
  this.setCollapsed(false);
}, true);
```

**测试**：`test/overlay-position.test.mjs` → 底部下限、底色、收起方向（换边要跟着换方向）、
构造时指定默认收起，共 5 条。

## 39. **补显通道会把逐字显示整个吞掉**——"做完了却没效果"的真身

这是本项里最隐蔽的一个坑，而且**单测永远发现不了**。

### 现象

逐字显示写好了、单测全绿，真机上却完全是老样子：**一句话整块蹦出来**。

### 真因

渲染有**两条路**，而我只给其中一条装了逐字：

| 路径 | 触发条件 | 原来怎么显示 |
| --- | --- | --- |
| 正常路径（`renderFrame` 末尾 + held 分支） | `segmentAt()` 命中，或保留最近一条 | **已改成逐字** |
| 补显通道（`drainCatchUpQueue`） | `segment.end <= 当前播放时间` | `show(segment.text)` ——**整句直接上屏** |

关键在于第二条的**触发条件**：识别慢一两句是常态，所以"这一段的结束时间已经早于
播放位置"**几乎对每一句都成立**。于是真实运行里**几乎每一句都走补显通道**，
正常路径根本没轮到——逐字等于没做。

单测为什么发现不了：测试里是直接调 `renderFrame()` 喂一条轨数据，
`enqueueLaggingSegments` 那步是手动调的、或者干脆没调，于是走的是正常路径。
**两条路在测试里没有交汇。**

### 怎么发现的

写了个时间轴推演脚本 `tools/sim-timeline.mjs`：按真实节奏（每 6 秒一块、
延迟 5 秒、句子按块一起回来）驱动 `renderFrame`，把屏幕上出现过的内容按时间打出来。
第一版输出是这样的——每行都是一整句，没有一行是半句：

```
111.00s | 好,我们来看这个图啊,我们看这个什么是欠拟合.
115.00s | 就是说,模型的复杂度不够的时候,训练误差下不去.
121.50s | 然后呢,随着模型复杂度提高,训练误差会一直减小.
```

**一眼就能看出逐字没生效**，而单测里一切正常。

### 改法（两条路都要逐字，但节奏可以不同）

1. **只剩一条时补显通道不接管**（`backlog === 1 → return false`，交回正常路径）：
   一条迟到不算积压，让它按自己的语速逐字打完。
2. **真积压（≥2 条）时接管，但也逐字**：把这句话的放字时长压缩到 `dwell` 之内
   （`typewriterSlice(seg, time, dwell/1000)`），积压越多打得越快。
   这样既保住"一个字一个字出来"，又不会像按原速补显那样永远追不平（见 #30）。
3. 补显的**换条**有节流，但**逐字进度不能跟着冻住**——所以单独存一份
   `catchUpItem`，节流只决定"什么时候换下一条"，每一帧仍然推进正在打的那句。

### 附带的教训

**"逻辑正确"和"生效"是两件事。** 一个分支写得再对，只要它的触发条件在真实数据下
永远不成立，就等于没写。这类问题必须用**按真实节奏推演**的手段去抓，
光靠"给定输入断言输出"的单元测试抓不到。

## 40. 「落后上限」的取值不能再按分块时长算（它会截断正在打的句子）

同一个推演脚本揪出来的第二个问题。

原来的算法：

```js
computeMaxLagSeconds() { return Math.max(6, chunkSeconds); }
```

它的语义是"落后不超过再来一块就能补上的范围"。**加了逐字之后这条前提失效了**：

```
屏幕上的内容本来就比话音晚 ≈ 识别延迟 + 最多一个分块
6 秒分块 + 5 秒识别延迟 ≈ 常态 11 秒          ← 这是上游延迟，不是"我们没跟上"
旧阈值 = max(6, 6) = 6 秒                    ← 卡在常态值以下
```

于是它**每几秒就触发一次**"跳过历史、直接对齐最新"，把正在逐字打的那句
**拦腰截断**。屏幕上的表现是"一句话打到一半忽然跳到下一句"。
（推演日志里那一行 `字幕落后约 6.3s，超过上限 6s` 就是在报这件事。）

**两处修改**：

1. 阈值改为 `Math.max(20, chunkSeconds * 2 + 8)` —— 只当"再来好几块也补不上"时才动手，
   日常的追赶交给补显通道的加速打字去自我纠正。
2. 触发条件加上 `catchUpQueue.length >= 2` ——
   **能不能跟上要看积压，不看时间**。只有一条迟到是上游延迟的必然结果，
   永远不该因此跳历史。

**判据**：日志里不应再频繁出现「字幕落后约 …超过上限…」；
出现了要看紧随其后的字幕是不是被截断。
