> **采集窗口没跟着降级回滚**（见 gotchas #34）。已修，并用
> `test/streaming-fallback.test.mjs` 守住。下面的验收清单仍然适用。

**为什么最优先**：本地识别服务我单独验证过了（6.6 秒语音 1.91 秒识别完，关键词命中 4/5），
但“**扩展 → 本地服务 → 字幕显示**”这条完整路径**还没在真实课程上跑过**。
这是目前唯一的功能性缺口。

**第二轮已经按用户实测反馈修了 5 处**（字幕轨乱序、追赶补显、重复解码、暂停留洞、
墙钟分块，见 handoff「第二轮修改」一节）；**第三轮又修了采集侧的“覆盖不变式”**
（绝不关掉最后一个录音窗口，见 handoff「第三轮修改」）。但**都只在单元测试里验证过**。
所以这一轮的回归要把它们一起验掉。

**预期**：总延迟约 6~10 秒（分块秒数 + 识别耗时），字幕**一句接一句连续显示**，
并且**不再出现整段内容缺失**。

**第五轮新增了「流式识别」模式**（默认开，见 handoff「第五轮修改」）。它把分块从
「整块等」改成「小切片连续投喂 + 服务端滚动解码」，**连续性更好、时间戳更准**，
但**首次出字幕的地板仍在 5 秒左右**——那是 Whisper 对短音频的输出稳定性决定的，
不是架构能优化的（实测数据见 `docs/gotchas.md` #33）。所以「几秒延迟」在这一轮
**并没有消失**，只是变得平滑。**要真正归零必须做 P0.5。**

**完整步骤见 [docs/verify-round3.md](verify-round3.md)**（含分块与流式两组场景与判读表）。

**怎么验证**：

```powershell
# 1. 起服务（保持窗口开着）
python tools\local-asr\server.py

# 2. 扩展侧：打包 → 刷新扩展 → 刷新页面
node tools/build.mjs
# chrome://extensions 点刷新 → 视频页面按 F5

# 3. 确认设置里供应商是「本地 Whisper」、API Key 为空
# 4. 播放视频 → 开启字幕 → 连续跑 60 秒以上
#    （建议先用 1 倍速跑一遍，再用你平时看的倍速跑一遍）
# 5. 中途按一次暂停、再恢复，专门看暂停点前后有没有缺内容
# 6. 最后点「导出 SRT」，把导出文本和视频对照一遍 —— 这是判断“有没有缺内容”最硬的证据
```

**要看的数据**（Console 里）：

```
[字幕助手] 分块设置：每块 6s 音频，重叠 1s          ← 新增：块长该等于它
[字幕助手] 第 N 块：?s→?s，?KB，音频 ?.?s           ← 音频时长应稳定接近上面的分块秒数
[字幕助手] 第 N 块识别耗时 ?s，视频进度 ?s（该块覆盖 ?s→?s，落后约 ?s）
[字幕助手] 有 N 条字幕已落后于画面，将按顺序补显（当前积压 N 条）
[字幕助手] ⚠ 分块节拍被推迟 X.Xs / ⚠ 第 N 块超长     ← 新增：出现就说明页面卡了
[字幕助手] ⚠ 采集空档 a→b                            ← 新增：这段音频真的没录到
[字幕助手] ⚠ 第 N 块文字偏少：X 字 / Ys ≈ Z 字/秒     ← 新增：Z 低于 1.2 才打
[本地识别] ?s，音频 ?s，速度 ?x 实时 → ……
[字幕助手] 已停止。……延迟归因：等分块约 ?s + 服务识别平均 ?s ≈ 共 ?s
```

**判断标准**：
- **「分块设置」里的秒数要和你设的一致**；块长明显超出它就是采集侧的问题，不用查服务
- 识别耗时应稳定在 **1.4~2.5 秒**（若明显更慢，检查是否误连了云端）
- “落后”应在 **6~10 秒**（若仍是 15 秒以上，说明本地服务没被用上）
- 字幕应**一句接一句连续显示**，不再有大片空白
- **暂停一次再恢复，暂停点前后不该缺内容**（第 4 处修复的验收点）
- **`__ZIMU__.inspect()` 里「采集空档」应为 0 处**（第三轮的核心验收点）。
  不为 0 就说明那几段音频确实没被录到——这是采集问题，不是识别问题
- 「待补显字幕」持续为 0 或偶尔跳到个位数属于正常；**持续几十条**说明识别长期跟不上
  （此时先调小分块秒数，或把模型换成 `tiny`/`base` 试吞吐）

**如果识别耗时本身正常、但延迟仍偏高**：把设置里「分块秒数」从 6 调到 **4**，总延迟可再降约 2 秒。

**如果「⚠ 分块节拍被推迟」反复出现**：说明页面主线程在跑重任务（这个学习平台内嵌了
Python 笔记本）。先用下面的命令确认识别服务本身没问题：

```powershell
python tools\local-asr\verify-speech.py     # 给出「速度 ?x 实时」，不受页面影响
```

若这里能跑到 3 倍实时、而扩展日志里只有 1 倍，就是页面在抢 CPU，不是识别服务的问题。

## P0.5：预转写模式（**现在是「零延迟」的唯一出路**，待可行性验证）

**为什么升格**：第五轮把「流式识别」做完了，实测却证明实时链路的地板
就是 Whisper 对短音频的输出稳定性（约 5 秒，见 gotchas #33）。
也就是说**「边播边录」这条路上，几秒延迟是消除不掉的**。
要真正做到「字幕与语音同步」，只剩「提前拿到整片音频、预先转写」这一条路。

**背景**：现在的架构是「边播边录、录一段识别一段」，所以
`延迟 ≈ 分块秒数 + 识别耗时` 是**架构决定的下限**，调参只能逼近、不能消除。

**用户的构想（方向正确）**：进入页面后先把**整段音频**取下来、提前全部转写成带时间戳的
字幕，播放时只是「按 `currentTime` 查表显示」——延迟归零，也不再需要追赶队列。

**关键前提（必须先量，别先写代码）**：能否整段拿到音频。三种结果三条路：

| 结果 | 判定依据 | 走法 |
| --- | --- | --- |
| 容易 | `currentSrc` 是 mp4/webm/m4a，直接 fetch 得到整段字节 | 下载 → `decodeAudioData` → 切片送本地服务 → 生成字幕轨 |
| 要费劲 | 是 HLS(m3u8)/DASH 清单，或源是 `blob:` | 拉清单 → 拼分片 → 再解码 |
| 走不通 | DRM 加密、直播流、音频由页面实时合成 | 继续用现有的实时方案 |

**已有工具**：`tools/prefetch-probe.js` —— 整段粘到视频页面的 Console 里执行，
一次性给出上面的判定（含解码验证与转写耗时估算）。

**实现要点（确认可行后再动手）**：

- 下载与解码要放在 **background**：页面上下文的 `fetch` 受同源策略限制，
  扩展的 background 带 host 权限才可以绕过 CORS。
- 大文件必须**分段**处理与传输（1 小时音频约 115MB WAV），避免内存与消息体超限。
- 想让字幕时间点精确，需要本地服务返回 **segment 级时间戳**。
  **第五轮已经做了**：`/v1/audio/stream` 返回的每一段都带服务端算出的真实起止时间
  （`{start,end,text}`），预转写可以直接复用这套返回结构，不必另起接口。
- UI 需要「预转写进度」：整段转写通常要几分钟，可以**边转边播**（只要转写进度领先播放位置）。

**不适用**：直播、DRM 保护的课程、以及音频由页面实时生成的场景。

## P1：实时追赶的取舍（第四轮已改，留待实测调参）

**背景**：现在有三层机制在保连贯——① 每条补足**最短显示时长**；
② 显示后**保留到被更新的内容替换**（不再有“持有上限”，见 gotchas #31）；
③ 识别落后时由**追赶队列**逐条补显，但**落后超过 `maxLagSeconds` 就跳历史、对齐最新**
（第四轮新增，见 gotchas #30）。

**核心取舍**：屏幕的“及时”和“完整”在这里是冲突的，
`maxLagSeconds = max(6, chunkSeconds)` 就是那条分界线：

- **调大**（例如 ×2）：更多迟到的内容会被逐条补显，字幕更完整，但屏幕更滞后。
- **调小**（例如 4）：更快对上画面，但落后期间的内容只会出现在导出的 SRT 里。

**怎么定**：到真实课程上看哪种感受更能接受——这正是需要用户判断的事，
不要凭代码推演拍板。

**顺带**：`catchUpDwellFor()` 的“半速补显”有 700ms 下限。若实测发现补显太快
来不及读，把 `catchUpMinDwellMs` 调大即可。

**注意**：改这块之前先看 `docs/gotchas.md` 第 9、22、30、31 条，避免把已修好的行为改回去。

## P2：识别准确性（第六轮已做了一半：模型可选了，后处理还没做）

### 已做（第六轮）

识别服务的**模型现在是可选的**，设置面板里直接下拉，包含：

> 选型对照（含误差率图表与逐条点评）见 **[model-comparison.html](model-comparison.html)**。

| 预设 | 地址 | 模型 | 协议 |
| --- | --- | --- | --- |
| 硅基流动 · Qwen3-ASR-1.7B ★首推 | api.siliconflow.cn/v1 | `Qwen/Qwen3-ASR-1.7B` | transcriptions |
| 硅基流动 · 星辰 V3.2-Ultra | api.siliconflow.cn/v1 | `XingChenAGI/XingChenASR-V3.2-Ultra` | transcriptions |
| 阿里云百炼 · qwen3-asr-flash | dashscope.aliyuncs.com/compatible-mode/v1 | `qwen3-asr-flash` | **chat** |
| 阿里云百炼 · Fun-ASR（实验性） | 同上 | `fun-asr` | **chat** |
| 硅基流动 · SenseVoiceSmall（原默认） | api.siliconflow.cn/v1 | `FunAudioLLM/SenseVoiceSmall` | transcriptions |

为此新增了 `apiStyle`（`transcriptions` / `chat`）配置：
百炼的 `qwen3-asr-flash` **没有** `/audio/transcriptions` 这个口子，
音频要从 `/chat/completions` 的 `messages[].content[].input_audio.data` 进去
（data URI 形式）。选错协议的报错很干净，所以设置面板会把**实际请求地址**
显示出来，方便对照。

**为什么换模型能治错字**：SenseVoiceSmall 只有 234M 且**不用上下文**，
中文 CER ~3.0%；Qwen3-ASR-1.7B 是 ~1.58%（差近一倍），
在会议/带口音/带背景音的课堂素材上差距更大。数据见 `docs/gotchas.md` #35。

**顺带修掉的真因**：错字漏字的主因其实是**采集窗口没回滚**
（见 gotchas #34）——降级到分块模式后仍在用 1.6 秒切片，
一句话被切碎送识别。**这个比换模型影响更大，已修**。

## 明确不做的事（附理由）

| 不做 | 理由 |
| --- | --- |
| 试图优化云端识别的延迟 | 8~15 秒全花在服务端排队，插件层面无法优化。**已用本地 Whisper 绕过** |
| 换云端模型来降延迟 | 同上；延迟由「分块秒数 + 服务端排队」决定，模型多准都一样。**但换模型能提高准确率**，第六轮已经做了（见 P2） |
| 给 `faster-whisper` 升级/降级 `av` | 降级在 Python 3.13 上没预编译包；现有兼容层已验证可用 |
| 用 headless 浏览器自动化验证扩展 | 本机 Edge 不支持 `--load-extension`（见 gotchas #19） |
| 引入流式 ASR | **第五轮已经做了**（`/v1/audio/stream`，默认开）。但要认清它的收益边界：买到的是连续性与时间戳准确性，**不是**更低的首次延迟（地板约 5s，见 gotchas #33） |
| 显示「未定稿」的流式文字（边解码边往屏幕上吐） | 实测未定稿文本很吵：缓冲 2 秒时模型会给出**错误词**（「现象」），3 秒时截断。提前显示会带来闪烁与错字，收益（感知延迟 −2~3s）与观感损失需要用户判断，**没做**。若要做，服务端已在响应的 `pending` 字段里返回了未定稿文本 |
| 给转写请求加并发上限 / 主动丢块 | P0 回归前不做。加上限等于主动丢内容，与用户“要完整”的诉求相冲；先把积压量暴露出来（`__ZIMU__.inspect()` 的「待补显字幕」），拿到真实数据再决定 |
| 在主线程被占死时强行缩短块长 | 第三轮定下的取舍：**完整性优先**。宁可块录长（识别慢、延迟高），也不留采集空档（内容永久缺失）。见 gotchas #26 |
