本轮修的是**字幕不连贯 / 中间内容缺失**，共 5 处结构性缺陷：

| # | 文件 | 缺陷 | 症状 |
| --- | --- | --- | --- |
| 1 | `common/transcript.js` | 字幕轨无脑追加，乱序块破坏二分查找 | 整条字幕被跳过 |
| 2 | `content/subtitles.js` | 落后的块只会显示最后一句，其余永远上不了屏 | “中间那段直接不显示” |
| 3 | `content/wav-encoder.js` + `subtitles.js` | 同一块音频解码 3 次（全在主线程） | 主线程卡 → 分块定时器推迟 → 音频空洞 |
| 4 | `content/capture.js` | 暂停恢复后故意等满一个分块周期 | 每次暂停挖掉一个 chunkSeconds 的洞 |
| 5 | `content/capture.js` | 分块按墙钟计时（语义应是媒体时间） | 倍速下块长翻倍、窗口被跳过 |

**第四轮（用户反馈“还是会输不全”后）又修了采集侧 3 处**：

| # | 文件 | 缺陷 | 症状 |

**验证目标**：确认真实课程上“字幕一句接一句连续显示”，且中途暂停/倍速/拖进度都不再缺内容。

## 第 4 步 · 端到端验证（核心，请按场景逐条跑）

打开一个**有中文字幕需求的教学视频**（能出声音、语速正常），按 `Alt+Shift+Z` 唤出面板。
每次开测前先 **F5 刷新页面**，然后打开 F12 → Console 面板（日志前缀都是 `[字幕助手]`）。

### 场景 A · 正常播放（1x，跑 60 秒以上）

操作：点「开启字幕」→ 让视频正常播放，不要暂停、不要动进度。

**看这三行日志**：

```
[字幕助手] 第 3 块：60.0s→66.0s，96KB，音频 6.0s        ← 块长应≈分块秒数
[字幕助手] 第 3 块识别耗时 1.8s，视频进度 68.4s（该块覆盖 60.0s→66.0s，落后约 2.4s）
[字幕助手] 第 3 块识别到：xxx（拆成 2 条字幕）
```

**判读**：

| 指标 | 正常 | 异常 → 怎么办 |
| --- | --- | --- |
| 块的「音频 X.Xs」 | 稳定 ≈ 6.0s（±1） | 明显 >10s：倍速/墙钟修复未生效，发日志给我 |
| 识别耗时 | 1.4~2.5s | >5s 且递增：走的是云端或服务在排队，检查供应商设置 |
| 落后约 | 6~9s | 长期 15s+：本地服务没被用上 |
| 字幕观感 | 一句接一句，无长空白 | 仍有整段空白 → 进场景 B 判断 |

### 场景 B · 暂停恢复（**本轮重点**）

操作：正常播放 → **暂停 3 秒** → 继续播放 → 再跑 30 秒。

**必须看到这两行**：

```
[字幕助手] 视频暂停，暂停期间不再切新块
[字幕助手] 视频恢复播放，立刻继续分块
```

**验收要点**：恢复播放后的**第一块**起始时间，应当**紧接暂停点**，
中间**不该出现一个 6 秒的空白区间**（这是缺陷 #4）。

- ✅ 合格：`第 N 块：210.3s → 214.0s`（约 3.7s，偏短正常，说明立刻开录了）
- ❌ 不合格：暂停在 210s，恢复后第一块却从 **216s** 开始 → 说明洞还在，发日志给我

### 场景 C · 倍速播放（本轮重点）

操作：把播放器调到 **1.5x 或 2x** → 再跑 30 秒。

**必须看到**（仅在倍速≠1x 时打印）：

```
[字幕助手] 当前播放倍速 2x：每块仍然是 6 秒音频，但请求会更密集
```

**验收要点**：每块的「音频 X.Xs」**仍然 ≈ 6.0s**，不随倍速放大（这是缺陷 #5）。

- ✅ 合格：倍速 2x 下，块长稳定 6s 上下、块与块的媒体时间**连续无跳号**（60→66→72…）
- ❌ 不合格：出现 `72s→84.9s` 这种 12 秒的块，或时间戳出现跳跃 → 发日志给我

### 场景 D · 拖动进度条

操作：拖到视频另一个位置 → 继续播放 20 秒。

**期望**：

- Console 打印 `进度跳转到 xxx.xs`
- 进度跳转**之前**残留的追赶字幕被清掉（诊断行「待补显字幕」应回到 0）
- 跳转后从新位置重新出字幕，**不会**把旧位置的字幕补出来

### 场景 E · 导出 SRT 对照（最硬的证据）

跑完 A~D 后，点面板「导出字幕」得到 `.srt`，用播放器加载或对照视频检查：

- 对照视频中段（尤其是**暂停点、倍速段、拖拽点**前后），字幕**不应有整句缺失**
- 时间轴连续，不出现“某两句之间空一大截”

> 判断“有没有缺内容”，SRT 对照是最终依据；屏幕观感受补显节奏影响，可能有滞后属正常。

### 场景 F · 采集空档自检（**第三轮核心**）

这一项专门验「输不全」。**开播时就盯着 Console**，整场跑完后检查有没有出现：

```
[字幕助手] ⚠ 采集空档 210.5s → 218.2s（7.7s 音频没被录到）。这段内容不会出现在字幕里——通常是分块节拍被推迟，检查页面是否在跑耗时任务
```

- ✅ 合格：**一次都不出现**。跑完点面板「停止」，汇总里也不该出现
  `⚠ 本次采集有 N 处空档`
- ❌ 不合格：出现了 → 把这两行连同 `__ZIMU__.inspect()` 一起发我。
  这**不是识别不准**，是那几段音频确实没被录到（详见 gotchas #26）

顺带记录这两类告警出现的**频率**（它们说明页面主线程被占）：

```
[字幕助手] ⚠ 分块节拍被推迟 X.Xs（页面主线程繁忙或定时器被节流）
[字幕助手] ⚠ 第 N 块超长：X.Xs（目标 6s）
```

偶发一两次可以接受；**连续出现**说明这个学习平台在跑重任务，
按下面「延迟仍偏高时的调参」里的办法先分离原因。

### 场景 G · 分离「服务慢」还是「页面卡」（有告警时做）

停掉扩展（点面板停止），另开一个窗口直接测服务本身：

```powershell
cd "F:\Agent xiangmu\DSH project\zimu"
python tools\local-asr\verify-speech.py
```

看输出里的 `速度 ?.?x 实时`：

| 这一行 | 说明 | 结论 |
| --- | --- | --- |
| ≥ 3x 实时 | 服务本身很快 | 扩展里慢是**页面在抢 CPU**，不是识别服务的问题 |
| 明显 < 1x | 服务本身就慢 | 换小模型：`--model base`；或看是不是有别的程序在占 CPU |

### 场景 H · 流式识别是否生效（**第五轮核心**）

先确认设置里**「流式识别」是勾上的**（默认勾选），并且供应商是「本地 Whisper」。

开播后 Console 应出现：

```
[字幕助手] 流式识别已启用：每 1.6s 投喂一片（重叠 0.4s），服务端边解码边定稿。若本机服务不支持会自动退回分块模式。
[字幕助手] 第 N 片定稿 M 条：……（解码 ?ms，视频 ?.?s）｜未定稿：……
```

**判读**：

| 现象 | 说明 | 怎么办 |
| --- | --- | --- |
| 有「流式识别已启用」，**没有**「已退回分块模式」 | 流式在跑 | ✅ 正常 |
| 出现「本机服务不支持流式识别，已退回分块模式」 | 服务是旧版本 | 重启服务（`python tools\local-asr\server.py`）；它启动时会打印 `流式识别：http://127.0.0.1:8788/v1/audio/stream` |
| 出现「流式识别连续失败 5 次，已退回分块模式」 | 服务崩了或被占满 | 看服务窗口的报错；可先关掉流式开关用分块模式顶着 |
| 字幕里出现与内容**无关的短句**（如「字幕製作人」「今天的视频就到这里」） | 音乐/音效段的幻觉漏了出来 | 这是幻觉过滤没拦住，把那段日志发我（gotchas #32） |

**验收要点**：

- 首次字幕出现后，字幕应**持续小步更新**（每几秒一条），而不是「等一大块再一起冒出来」
- **首次字幕仍在 5 秒左右**属于**正常**，不是 bug（gotchas #33）
- 面板「停止」后 Console 应出现：

```
[字幕助手] 流式统计：投喂 N 片，定稿 M 条，失败 0 片，服务端平均解码 ?ms
[字幕助手] 流式延迟归因：等一片约 1.6s + 服务识别平均 ?s ≈ 共 ?s。…
```

**想对比两种模式**：把「流式识别」取消勾选 → 刷新扩展 → F5，就是原来的分块模式；
两种模式的时间戳都能导出 SRT 对照。

### 场景 I · 云端供应商下的分块长度（**第六轮核心**）

这一场景专门验「错字漏字」的真因有没有被真正修掉。

**准备**：设置里选一个**云端**供应商（例如「硅基流动 · Qwen3-ASR-1.7B」），
「流式识别」**保持勾选**（默认就是勾上的，不用管它），填好 Key，保存 → 刷新扩展 → F5。

**开播后 Console 应当是这两行的样子**：

```
[字幕助手] 识别服务在云端：流式只对本机服务生效，本次直接按分块模式运行（每块 6s）。
[字幕助手] 分块设置：每块 6s 音频，重叠 1s（每块的「音频 X.Xs」应稳定接近 6s，明显超出即为异常）
[字幕助手] 第 0 块：273.0s→279.0s，…KB，音频 6.0s
```

**判读**：

| 现象 | 说明 | 怎么办 |
| --- | --- | --- |
| 「第 N 块」的**音频时长 ≈ 6s**（你设的分块秒数） | ✅ **本轮修对了** | 继续观察错字是否减少 |
| 「第 N 块」的音频时长是 **1.6s 左右** | ❌ **回滚没生效**（gotchas #34），一句话被反复切断 | 重新 `node tools/build.mjs` + 刷新扩展，然后回来重测 |
| 出现「流式识别不可用（…已退回分块模式）：每块改回 6s」 | 第二层防线在工作（正常） | 看**紧接着的下一块**是不是 6s；是就说明回滚成功 |
| 上游报 `400 / 404` | 协议或模型名不对 | 设置面板下方会显示**实际请求地址**，拿它和账单页面对照；百炼必须选 chat 协议 |

**验收要点**：

- 整段日志里，**每一块的「音频 ?.?s」都应接近你设的分块秒数**，
  不允许出现成群的小块（那是句子被切碎的直接证据）
- 换模型前后各跑 60 秒，**对照错字数量**
  （SenseVoiceSmall → Qwen3-ASR-1.7B 大约能减半，见 gotchas #35）
- 换模型**不会**让字幕更早出现，延迟仍在几秒量级；若你以为换模型能消掉延迟，那是误解

## 延迟仍偏高时的调参

> **先认清天花板**：Whisper 对短音频的输出稳定性决定了「首次字幕约 5 秒」这个地板
> （实测数据见 gotchas #33）。下面的调参只能让过程更平滑，**不能突破这个地板**。
> 想要「几乎同步」，唯一的路是 roadmap P0.5 的预转写。

若是**流式模式**（默认）：

- 把设置里**「流式切片」从 1.6 调到 1.0**：更新更频繁，但 CPU 占用上升
- 若服务端平均解码耗时 >1s：说明机器吃力，把 **streaming 关掉**用分块模式，或换 `--model base`

若是**分块模式**：

- 设置里把**分块秒数 6 → 4**，总延迟可再降约 2 秒
- 倍速播放本身会让请求变密，若服务跟不上，**降到 1x** 观察

若出现 `⚠ 分块节拍被推迟`（页面主线程被占）：

- 先按场景 G 用 `verify-speech.py` 脱离页面测一次，确认服务本身的速度
- 若服务能跑到 3x 实时、扩展里却只有 1x，那是页面在抢 CPU。
  这种情况下块会被录长、延迟会升，但**内容不会丢**（这是刻意的取舍，见 gotchas #26）

若识别耗时本身 >5s：问题在服务侧（走成了云端或机器排队），
不是本轮改动能解决的，先确认供应商是「本地 Whisper」且服务在跑。
